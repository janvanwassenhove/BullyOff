# ADR-009 — i18n approach: NL / EN / FR from day one

**Status:** Accepted · 2026-08-18
**Decides:** BRIEF §3 item 6, §8 Phase 9.

## Context

The default world is Belgian-shaped, and Belgian hockey is bilingual (NL/FR) with English as the lingua franca of the sport (FIH). All three ship in v1.0. Retrofitting i18n onto an app that hard-codes strings is a full pass over every component; doing it from the first component is nearly free. Hockey also has domain vocabulary that must be *right* in each language (NL "strafcorner", FR "petit corner", EN "penalty corner"; NL "cirkel", FR "cercle"…), and generated commentary needs pluralisation, gendered agreement (FR), and number/date formatting.

There is a subtlety: the engine emits *events*, not *text* (ADR-002). Commentary is a *consumer* of the log, so localisation of match text is a renderer/UI concern, never an engine one.

## Options considered

### A. Hard-code English, translate "later"
- Rejected. "Later" never comes, and NL/FR are half the target audience.

### B. vue-i18n
- **For:** the de-facto Vue library; ICU-ish message format with plurals; lazy-loaded locale files; composition API `useI18n()`; typed message keys with a bit of setup.
- **Against:** a runtime dependency (~10 kB gz with the compiler off); some API churn between majors. Both acceptable in the app layer (not the engine).

### C. Hand-rolled `t(key, params)` with JSON dictionaries
- **For:** zero deps, total control.
- **Against:** plurals, gender, and interpolation for three languages is exactly the wheel vue-i18n has already built and debugged. Solo dev; not worth it.

### D. Fluent (Project Fluent) via `@fluent/vue`
- **For:** best-in-class grammar handling (gender, plurals, selectors).
- **Against:** less mainstream in the Vue world, smaller ecosystem, another syntax to learn. Marginal benefit over ICU MessageFormat for our three languages.

## Decision

- **vue-i18n** in `apps/manager` (and later `arcade`), composition mode, message compilation at build time (`@intlify/unplugin-vue-i18n`) so the runtime message compiler is not shipped.
- **Locales:** `en` (source of truth, written first), `nl-BE`, `fr-BE`. Files: `apps/manager/src/locales/{en,nl-BE,fr-BE}/*.json`, split by feature (`common`, `match`, `squad`, `season`, …). Lazy-loaded per locale.
- **Typed keys:** a generated `MessageSchema` type from `en` so `t('match.penaltyCorner')` is checked; a missing key in NL/FR is a **CI failure**, not a runtime fallback (a `pnpm i18n:check` script, Phase 6).
- **The engine emits no strings.** Commentary is generated in the app from `MatchEvent[]` through locale-aware templates; player and club names are data, not translations. Hockey terms get a curated glossary file per locale, reviewed by a native speaker before Phase 9.
- **Formatting:** `Intl.NumberFormat`, `Intl.DateTimeFormat`, `Intl.RelativeTimeFormat` via vue-i18n's `n()`/`d()`; never manual string formatting.
- **Locale detection:** `navigator.language` → best match → persisted user override in settings (ADR-007).
- **Generated names** (worldgen) are *not* localised — a fictional Flemish player has the same name in the FR UI. Club nicknames/mottos, if any, may be locale-aware in v1.x.

## Consequences

- From the first Vue component in Phase 5/6, every user-visible string goes through `t()`. Lint: `vue-i18n`'s `no-raw-text` rule enabled for `.vue` templates when the dependency lands (Phase 5).
- Phase 9's "NL/EN/FR complete" gate becomes a mechanical check, not a translation project.
- Cost: a dependency in the app layer and a discipline tax on every string. Accepted.
- Not decided here: voice/audio localisation (umpire calls, crowd) — ADR-013 territory; likely language-neutral SFX in v1.0.
